## Question

User: "some label + entity, or just entities" and feature is optional. Make the rule exact:

- field level: is `linkableTo()` presence the only opt-in, or also `->entitiesRequired()`-style enforcement (every shape must carry an entity)? default off
- label level: is the *label* required when an entity is linked? (round-1: coexist, label can stay empty → entity-only "labels")
- does entity-only affect the Labels panel grouping (group by entity instead of/in addition to string label? pill text when label empty — record display string?)
- validation surface: Filament field `required` semantics unchanged? saving with links but zero labels allowed?

## Answer

Grilling 2026-10-08 — all four recommendations accepted.

- **No required mode.** Presence of `linkableTo()` is the only opt-in; no `entitiesRequired()`. Stricter rules are the developer's validation closure. Rationale reinforced: round-1's dangling-nulling (Q5a) makes hard-required semantics leaky anyway (a record delete would violate the rule without user action).
- **Seeding wins over entity-only.** wf-002 stands: first bind fills empty label with record display string; existing labels never touched. "Entity-only" shapes are not a state — they are a display concern (chip) layered on named shapes. Side effect embraced: same entity display string hashes to the same color across photos.
- **Validation semantics unchanged.** `required()` = at least one shape, as today. No label/entity requiredness introduced anywhere.
- **Stale allow-list links render anyway.** Read path never re-validates `linkableTo()`; only the picker filters to the current list. Chip + unlink remain available for links to types the developer later removed. No pruning on load or save.

Note for downstream tickets: with seeding, entity display strings appear among ordinary labels in the Labels panel — the grouping/identity question belongs to Labels panel (wf-008), now unblocked.
